# 결정 기록

평가 기준에 "사용한 기술을 왜 선택했는지 설명할 수 있는가"가 있다. 결정은 내린 그 작업에서 바로 기록한다. 끝에 몰아서 쓰지 않는다.

## 어디에 적나

| 결정 종류                                    | README 섹션                            |
| -------------------------------------------- | -------------------------------------- |
| 라이브러리·브라우저 API 선택                 | 기술 선택 이유                         |
| 폴더·모듈 경계 변경                          | 기술 선택 이유 > 폴더 구조와 의존 방향 |
| 동기화 흐름 (provider, 초기화, 탭 종료 처리) | 아키텍처 > 동기화 구조                 |
| X1~X3 동작                                   | 공동 편집과 AI가 만나는 지점           |
| 네트워크 확장 시 바뀌는 것                   | 실제 네트워크 기반 동기화로 확장한다면 |
| 구현하지 않은 것                             | 구현 범위                              |

명세 해석(D 항목)을 새로 정하거나 바꾸면 `docs/spec.md` "결정 사항" 표도 함께 고친다.

## 형식

```markdown
### <결정 한 줄>

<문제: 무엇을 정해야 했나 1~2문장>

- **선택**: <무엇을, 어떻게>
- **검토한 대안**: <대안> — <고르지 않은 이유>
- **트레이드오프**: <포기한 것>
```

- 이유는 이 과제의 요구사항이나 제약과 연결한다. "일반적으로 좋다"는 이유가 아니다.
- 코드와 문서가 어긋나면 안 된다. 구현을 바꿨으면 해당 기록도 고친다.
- 짧게 쓴다. 한 결정이 한 화면을 넘으면 핵심만 남긴다.

# Collaborative Spreadsheet

같은 브라우저의 여러 탭에서 동시에 편집하고, AI에게 편집을 요청할 수 있는 웹 스프레드시트입니다.

## 실행 방법

요구 사항: Node.js 20.9 이상 (`.nvmrc` 참고), pnpm

```bash
pnpm install
pnpm dev
```

| 스크립트                    | 설명                            |
| --------------------------- | ------------------------------- |
| `pnpm dev`                  | 개발 서버                       |

| `pnpm test`                 | Vitest 단위 테스트              |
| `pnpm format`               | Prettier 포맷                   |

## 기술 선택 이유

### 동기화: Yjs (CRDT)

탭마다 문서 복제본이 있고 각자 따로 편집되므로, 변경이 도착하는 순서가 탭마다 달라도 **모든 탭이 같은 결과로 수렴**해야 합니다. 받은 변경을 단순히 덮어쓰면 두 탭이 거의 동시에 같은 셀을 고쳤을 때 탭마다 다른 값이 남습니다.

Yjs는 변경마다 `(clientID, clock)` ID를 붙이고 모든 복제본이 같은 규칙으로 병합하는 CRDT입니다. 중앙에서 순서를 정해 주는 존재가 없어도 수렴하므로, 탭끼리 변경분만 주고받으면 됩니다.

직접 구현하는 대신 Yjs를 고른 결정적인 이유는 과제 요구사항 두 가지를 기본으로 지원하기 때문입니다.

- **내 변경만 되돌리는 undo**: `Y.UndoManager`에 `trackedOrigins`를 지정하면, 로컬에서 만든 변경만 undo 대상이 되고 다른 참여자의 변경은 건드리지 않습니다. 내가 바꾼 셀을 다른 사람이 다시 바꾼 경우의 처리도 라이브러리가 맡습니다. 동시편집 상황에서 직접 구현하면 버그가 가장 많이 나는 부분입니다.
- **AI 편집을 undo 한 번으로 되돌리기**: 적용을 하나의 `transact`로 묶고 앞뒤로 `stopCapturing()`을 호출하면 한 단위로 기록됩니다.

이 밖에 `y-indexeddb`(영속화)와 `y-protocols/awareness`(참여자 표시)가 같은 생태계에 있어 연결 비용이 작습니다.

셀은 `cells: Y.Map<"r:c", Y.Map>`처럼 셀마다 중첩된 `Y.Map`으로 저장합니다. 값(`v`)과 서식(`bold`, `italic`)이 서로 다른 키라서, 한 사람이 값을 바꾸는 동안 다른 사람이 굵게 처리해도 두 변경이 모두 남습니다. 같은 키를 동시에 바꾸면 한쪽이 결정적으로 선택됩니다(LWW).

### 저장소: IndexedDB

"모든 탭을 닫았다 열어도 유지"와 "새 탭에서 바로 보임"을 만족하려면, origin 안에서 탭 간에 공유되고 영구적으로 남는 저장소가 필요합니다.

| 저장소         | 판단                                                                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **IndexedDB**  | 탭 간 공유, 영구 보관, 비동기, 바이너리(`Uint8Array`) 저장, 트랜잭션 지원. `y-indexeddb`가 있음 → **선택**                                                                                      |
| localStorage   | 동기 API라 입력할 때마다 메인 스레드를 막음. 문자열만 저장돼 Yjs update를 base64로 변환해야 함(약 33% 증가). 용량 약 5MB. 키 하나를 통째로 덮어쓰는 구조라 두 탭이 동시에 쓰면 한쪽이 사라짐    |
| sessionStorage | 탭마다 분리되고 탭을 닫으면 삭제됨. 요구사항과 맞지 않음                                                                                                                                        |
| Cache Storage  | HTTP 요청/응답 캐시용. 데이터를 가짜 URL의 `Response`로 감싸야 하고, 트랜잭션과 순서 보장이 없어 압축 도중 중단되면 상태가 어긋날 수 있음                                                       |
| OPFS           | 파일 단위 API. 빠른 동기 쓰기는 전용 워커에서만 가능하고 파일에 배타적 잠금이 걸림. 비동기 쓰기는 닫을 때 파일을 통째로 교체해 여러 탭의 동시 쓰기를 직접 설계해야 함. Yjs 연동 라이브러리 없음 |

Yjs 저장은 "전체 상태 덮어쓰기"가 아니라 "변경분을 추가로 쌓고 가끔 압축하기"입니다. IndexedDB는 레코드 단위 추가와 트랜잭션을 지원해서 이 방식에 잘 맞고, 여러 탭이 같은 변경분을 중복으로 저장해도 Yjs update는 여러 번 적용해도 결과가 같아 문제가 없습니다.

IndexedDB에는 다른 탭의 변경을 알려주는 이벤트가 없으므로, 실시간 전파는 아래의 BroadcastChannel이 맡습니다.

### 전달: BroadcastChannel

같은 origin의 탭끼리 메시지를 주고받는 브라우저 API입니다. Yjs update와 awareness 메시지를 바이너리 그대로 실어 보냅니다.

`storage` 이벤트는 localStorage가 바뀔 때만 발생해서 문자열 변환과 동기 쓰기 비용이 따르고, `window.postMessage`는 `opener` 관계의 창끼리만 쓸 수 있어 실질적인 대안은 SharedWorker였습니다.

**SharedWorker 중앙 서버식과의 비교**

SharedWorker로는 CRDT 없이도 구현할 수 있습니다. 워커가 모든 탭의 편집을 받은 순서대로 적용하고 같은 순서로 다시 뿌리면 결과가 항상 일치합니다. 같은 기기 안이라 왕복이 짧아서, 응답을 받은 뒤 반영해도 체감 지연이 거의 없습니다.

|                 | Yjs + BroadcastChannel              | SharedWorker 중앙 서버식                                               |
| --------------- | ----------------------------------- | ---------------------------------------------------------------------- |
| 결과 일치       | Yjs가 보장                          | 워커가 순서를 정해 보장                                                |
| 새 탭 초기 상태 | IndexedDB 로드 + 채널로 누락분 요청 | 워커가 현재 상태를 바로 전달                                           |
| 내 변경만 undo  | `UndoManager` 설정                  | 참여자별 undo 스택, 역연산, 다른 사람이 덮어쓴 경우의 처리를 직접 구현 |
| 장애 영향       | 탭 하나가 죽어도 나머지는 정상      | 워커가 죽으면 전체 동기화가 멈춤                                       |
| 코드 버전       | 새로고침한 탭은 새 코드로 동작      | 탭이 하나라도 열려 있으면 옛 워커 코드가 계속 남음 (배포·HMR 시)       |
| 브라우저 지원   | 모든 주요 브라우저                  | Chrome Android 미지원                                                  |

SharedWorker의 장점인 "원본이 한 곳"과 "쓰는 곳이 한 곳"은 CRDT를 쓰면 필요 없어집니다. CRDT는 중앙 없이 동등한 복제본이 수렴하도록 만든 알고리즘이고, 중복 저장도 무해하기 때문입니다. 남는 것은 워커 코드와 단일 장애점이라는 비용뿐이라 BroadcastChannel을 선택했습니다. 특히 명세의 "내 변경만 undo"를 직접 구현하는 위험을 피하는 것이 컸습니다.

Yjs에는 BroadcastChannel 전용 provider가 없어 직접 작성합니다(`features/collab/broadcast-provider.ts`). `y-webrtc`도 내부에서 BroadcastChannel을 쓰지만, WebRTC 의존성이 딸려 오고 "브라우저 API만으로"라는 조건에서 동작을 명확히 설명하기 어려워 사용하지 않았습니다.

### 폴더 구조와 의존 방향

같이 바뀌는 코드끼리 모으기 위해 기술 종류(components, hooks 등)가 아니라 **기능 단위**로 나눴습니다.

```
src/
  app/                 # 라우트만
  features/
    sheet/             # 셀 주소·범위(model), Y.Doc 구조·편집 연산·undo(store), 그리드 UI(ui)
    collab/            # IndexedDB 영속화, BroadcastChannel 동기화, presence
    ai/                # (3단계) AI 편집
  session/             # 기능 조립: Y.Doc·저장·동기화·undo 생성과 해제
  shared/              # 기능과 무관한 공통 UI·유틸
```

```
ai ──→ sheet ←── collab/ui
         ↑
      session (조립)
```

- **`sheet`는 `collab`·`ai`를 모릅니다.** 탭이 하나든 여러 개든 똑같이 동작하는 편집 로직만 담습니다.
- **`collab` 코어는 Y.Doc만 다룹니다.** 셀이라는 개념을 몰라서, 네트워크 동기화로 확장할 때 이 폴더의 provider만 교체하면 됩니다. 그리드 위에 다른 참여자의 선택 범위를 그리는 `collab/ui`만 `sheet`의 공개 API를 사용합니다.
- **기능 사이의 연결은 `session`에서만** 합니다.
- **각 feature는 `index.ts`로만 공개**합니다. 내부 파일 직접 import와 위 의존 방향 위반은 ESLint `no-restricted-imports`로 막습니다.
- **그리드 위 표시는 레이어로 끼워 넣습니다.** `Grid`는 좌표 계산과 오버레이 자리만 제공하고, 다른 참여자의 선택 표시나 AI 제안 하이라이트는 각 feature가 자기 레이어로 전달합니다. `Grid`가 이들을 직접 import하면 `sheet`가 `collab`·`ai`에 의존하게 되기 때문입니다.
- 각 feature 안에서는 순수 로직(`model/`)과 외부에 닿는 코드(Yjs, IndexedDB, React)를 나눠 순수 로직을 단위 테스트합니다.

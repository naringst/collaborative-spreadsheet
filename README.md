# Collaborative Spreadsheet

같은 브라우저의 여러 탭에서 동시에 편집하고, AI에게 편집을 요청할 수 있는 웹 스프레드시트입니다.

## 실행 방법

요구 사항: Node.js 20.9 이상 (`.nvmrc` 참고), pnpm

```bash
pnpm install
pnpm dev
```

| 스크립트                    | 설명                            |
| --------------------------- | ------------------------------- |
| `pnpm dev`                  | 개발 서버                       |
| `pnpm build` / `pnpm start` | 프로덕션 빌드 / 실행            |
| `pnpm lint`                 | ESLint (feature 경계 규칙 포함) |
| `pnpm typecheck`            | TypeScript 타입 검사            |
| `pnpm test`                 | Vitest 단위 테스트              |
| `pnpm format`               | Prettier 포맷                   |

## 구현 범위

**구현한 것**: 시트 편집(선택·입력·키보드 이동·IME), 셀 서식(굵게·기울임·밑줄·취소선), 실행 취소/다시 실행, 영속화(IndexedDB), 탭 간 공동 편집(실시간 반영·참여자 표시·탭 종료 정리·내 변경만 undo), 여러 시트와 목록.

**의도적으로 제외한 것**:

- **시트 삭제(S8 P2)**: 열려 있는 다른 탭의 처리(강제 퇴장/not-found 전환), `sheet-{id}` IndexedDB 정리, 삭제·재생성 경합 등 새 동시성 표면을 만든다. P0·P1 대비 복잡도가 커서 제외했다.
- **수식(S2)**: `=SUM(...)`은 문자열로 저장만 하고 계산하지 않는다.
- **복사·붙여넣기, 열 너비 조절, 행·열 전체 선택 등(S7 P2)**: 핵심 완성도를 우선했다.

## 기술 선택 이유

### 동기화: Yjs (CRDT)

탭마다 문서 복제본이 있고 각자 따로 편집되므로, 변경이 도착하는 순서가 탭마다 달라도 **모든 탭이 같은 결과로 수렴**해야 합니다. 받은 변경을 단순히 덮어쓰면 두 탭이 거의 동시에 같은 셀을 고쳤을 때 탭마다 다른 값이 남습니다.

Yjs는 변경마다 `(clientID, clock)` ID를 붙이고 모든 복제본이 같은 규칙으로 병합하는 CRDT입니다. 중앙에서 순서를 정해 주는 존재가 없어도 수렴하므로, 탭끼리 변경분만 주고받으면 됩니다.

직접 구현하는 대신 Yjs를 고른 결정적인 이유는 과제 요구사항 두 가지를 기본으로 지원하기 때문입니다.

- **내 변경만 되돌리는 undo**: `Y.UndoManager`에 `trackedOrigins`를 지정하면, 로컬에서 만든 변경만 undo 대상이 되고 다른 참여자의 변경은 건드리지 않습니다. 내가 바꾼 셀을 다른 사람이 다시 바꾼 경우의 처리도 라이브러리가 맡습니다. 동시편집 상황에서 직접 구현하면 버그가 가장 많이 나는 부분입니다.
- **AI 편집을 undo 한 번으로 되돌리기**: 적용을 하나의 `transact`로 묶고 앞뒤로 `stopCapturing()`을 호출하면 한 단위로 기록됩니다.

이 밖에 `y-indexeddb`(영속화)와 `y-protocols/awareness`(참여자 표시)가 같은 생태계에 있어 연결 비용이 작습니다.

셀은 평탄화된 단일 맵에 `cells: Y.Map<"r:c:속성", 값>` 형태로 저장합니다 (값은 `"3:2:v"`, 서식은 `"3:2:bold"`). 값과 서식이 처음부터 서로 다른 최상위 키라서, 한 사람이 값을 바꾸는 동안 다른 사람이 굵게 처리해도 두 변경이 모두 남습니다. 같은 키를 동시에 바꾸면 한쪽이 결정적으로 선택됩니다(LWW). 이 구조를 고른 이유는 아래 "셀 저장 구조" 참고.

### 저장소: IndexedDB

"모든 탭을 닫았다 열어도 유지"와 "새 탭에서 바로 보임"을 만족하려면, origin 안에서 탭 간에 공유되고 영구적으로 남는 저장소가 필요합니다.

| 저장소         | 판단                                                                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **IndexedDB**  | 탭 간 공유, 영구 보관, 비동기, 바이너리(`Uint8Array`) 저장, 트랜잭션 지원. `y-indexeddb`가 있음 → **선택**                                                                                      |
| localStorage   | 동기 API라 입력할 때마다 메인 스레드를 막음. 문자열만 저장돼 Yjs update를 base64로 변환해야 함(약 33% 증가). 용량 약 5MB. 키 하나를 통째로 덮어쓰는 구조라 두 탭이 동시에 쓰면 한쪽이 사라짐    |
| sessionStorage | 탭마다 분리되고 탭을 닫으면 삭제됨. 요구사항과 맞지 않음                                                                                                                                        |
| Cache Storage  | HTTP 요청/응답 캐시용. 데이터를 가짜 URL의 `Response`로 감싸야 하고, 트랜잭션과 순서 보장이 없어 압축 도중 중단되면 상태가 어긋날 수 있음                                                       |
| OPFS           | 파일 단위 API. 빠른 동기 쓰기는 전용 워커에서만 가능하고 파일에 배타적 잠금이 걸림. 비동기 쓰기는 닫을 때 파일을 통째로 교체해 여러 탭의 동시 쓰기를 직접 설계해야 함. Yjs 연동 라이브러리 없음 |

Yjs 저장은 "전체 상태 덮어쓰기"가 아니라 "변경분을 추가로 쌓고 가끔 압축하기"입니다. IndexedDB는 레코드 단위 추가와 트랜잭션을 지원해서 이 방식에 잘 맞고, 여러 탭이 같은 변경분을 중복으로 저장해도 Yjs update는 여러 번 적용해도 결과가 같아 문제가 없습니다.

IndexedDB에는 다른 탭의 변경을 알려주는 이벤트가 없으므로, 실시간 전파는 아래의 BroadcastChannel이 맡습니다.

### 전달: BroadcastChannel

같은 origin의 탭끼리 메시지를 주고받는 브라우저 API입니다. Yjs update와 awareness 메시지를 바이너리 그대로 실어 보냅니다.

`storage` 이벤트는 localStorage가 바뀔 때만 발생해서 문자열 변환과 동기 쓰기 비용이 따르고, `window.postMessage`는 `opener` 관계의 창끼리만 쓸 수 있어 실질적인 대안은 SharedWorker였습니다.

**SharedWorker 중앙 서버식과의 비교**

SharedWorker로는 CRDT 없이도 구현할 수 있습니다. 워커가 모든 탭의 편집을 받은 순서대로 적용하고 같은 순서로 다시 뿌리면 결과가 항상 일치합니다. 같은 기기 안이라 왕복이 짧아서, 응답을 받은 뒤 반영해도 체감 지연이 거의 없습니다.

|                 | Yjs + BroadcastChannel              | SharedWorker 중앙 서버식                                               |
| --------------- | ----------------------------------- | ---------------------------------------------------------------------- |
| 결과 일치       | Yjs가 보장                          | 워커가 순서를 정해 보장                                                |
| 새 탭 초기 상태 | IndexedDB 로드 + 채널로 누락분 요청 | 워커가 현재 상태를 바로 전달                                           |
| 내 변경만 undo  | `UndoManager` 설정                  | 참여자별 undo 스택, 역연산, 다른 사람이 덮어쓴 경우의 처리를 직접 구현 |
| 장애 영향       | 탭 하나가 죽어도 나머지는 정상      | 워커가 죽으면 전체 동기화가 멈춤                                       |
| 코드 버전       | 새로고침한 탭은 새 코드로 동작      | 탭이 하나라도 열려 있으면 옛 워커 코드가 계속 남음 (배포·HMR 시)       |
| 브라우저 지원   | 모든 주요 브라우저                  | Chrome Android 미지원                                                  |

SharedWorker의 장점인 "원본이 한 곳"과 "쓰는 곳이 한 곳"은 CRDT를 쓰면 필요 없어집니다. CRDT는 중앙 없이 동등한 복제본이 수렴하도록 만든 알고리즘이고, 중복 저장도 무해하기 때문입니다. 남는 것은 워커 코드와 단일 장애점이라는 비용뿐이라 BroadcastChannel을 선택했습니다. 특히 명세의 "내 변경만 undo"를 직접 구현하는 위험을 피하는 것이 컸습니다.

Yjs에는 BroadcastChannel 전용 provider가 없어 직접 작성합니다(`features/collab/broadcast-provider.ts`). `y-webrtc`도 내부에서 BroadcastChannel을 쓰지만, WebRTC 의존성이 딸려 오고 "브라우저 API만으로"라는 조건에서 동작을 명확히 설명하기 어려워 사용하지 않았습니다.

### 참여자 표시: y-protocols/awareness

참여자 이름·색·선택 위치는 저장되지 않는 휘발 상태라 Y.Doc이 아닌 별도 채널이 필요합니다.

- **선택**: `y-protocols/awareness`. clock 기반 상태 병합, 제거 프로토콜, 타임아웃 정리가 이미 구현돼 있고 yjs와 같은 생태계라 추가 전송 의존성이 없다.
- **검토한 대안**: BroadcastChannel 위에 자작 presence 맵 — 순서·타임아웃·제거 전파를 다시 만들게 되어 Q2(재구현 금지) 위반.
- 커서 페이로드는 collab 코어에서 `unknown`으로 불투명하게 다룬다 — 코어는 셀 개념을 모른다는 경계 유지. 구체 타입은 sheet 공개 API를 쓸 수 있는 `collab/ui`에 있다.

### 탭 종료 감지: Web Locks (heartbeat 대신)

비정상 종료(크래시)된 참여자를 수 초 안에 지우되, 절전된 백그라운드 탭을 잘못 지우면 안 됩니다(C6).

- **선택**: 각 탭이 자기 clientID 이름의 Web Lock을 보유하고, 피어는 그 잠금을 요청해 둔다. 획득되는 순간이 곧 소유 탭의 사망이다 — 브라우저가 탭 종료 시 즉시 해제하고, 타이머 스로틀링과 무관하다.
- **검토한 대안**: heartbeat — 백그라운드 탭은 타이머가 최대 1분으로 스로틀링되어 살아 있는 탭이 오탐 제거된다.
- awareness의 30초 타임아웃도 같은 이유로 절전 탭을 오탐하므로, Web Locks가 있으면 원격 상태의 lastUpdated를 주기 갱신해 타임아웃을 무력화한다. Web Locks 미지원 환경에서만 타임아웃이 폴백으로 동작한다.

### 원격 update의 origin은 provider 인스턴스

- **선택**: 수신 update를 `Y.applyUpdate(doc, update, provider)`로 적용하고, `doc.on("update")`에서 origin이 자신이면 재전송하지 않는다. Yjs 표준 관례로, collab이 sheet의 심볼(`LOCAL_ORIGIN`)을 의존하지 않아도 에코 차단과 undo 제외(trackedOrigins)가 모두 성립한다.
- **검토한 대안**: `REMOTE_ORIGIN` 상수 — 의도는 같지만 collab에 별도 심볼이 생기고 provider가 여럿일 때 구분이 안 된다.

### 셀 저장 구조: 중첩 Y.Map 대신 평탄화 (`"r:c:속성"` 키)

셀을 어떻게 저장할지 두 가지를 검토했습니다: 셀마다 중첩 Y.Map을 두는 구조(`cells["3:2"] = Y.Map{v, bold}`)와, 속성까지 키에 넣어 한 겹으로 펴는 구조(`cells["3:2:v"]`, `cells["3:2:bold"]`).

- **선택**: 평탄화. 속성마다 처음부터 독립된 최상위 키라서 어떤 동시 편집 조합에서도 키 단위로만 병합된다.
- **검토한 대안**: 중첩 Y.Map — 셀이라는 타입 경계가 코드에 보이고 셀 단위 순회가 자연스럽지만, 두 가지 실제 문제를 만들었다.
  1. **동시 최초 생성 소실**: 두 탭이 같은 빈 셀에 동시에 값·서식을 넣으면 각자 만든 중첩 Y.Map(컨테이너)이 최상위 키에서 LWW로 충돌해 한쪽 내용이 통째로 사라진다 — C3("값과 서식을 동시에 바꾸면 모두 반영")·S4("독립 병합") 위반.
  2. **undo가 컨테이너째 지움 (D7)**: 빈 셀에 처음 값을 넣은 편집을 undo하면 컨테이너 삽입까지 되돌아가, 그 사이 다른 참여자가 덮어쓴 값도 함께 사라진다(단위 테스트로 발견). 컨테이너 생성을 별도 origin으로 분리하는 보정이 필요했다.
- **이유**: 평탄화는 두 문제가 구조적으로 존재하지 않아 보정 코드(별도 origin, 복구 로직)가 필요 없다. 평가 기준이 "불필요한 복잡도를 걷어냈는가"(Q2)이므로, 셀 순회 시 키 파싱 한 겹(`parseCellKey`)을 감수하고 특수 처리 두 개를 없애는 쪽을 골랐다.
- **트레이드오프**: "한 셀의 모든 속성" 같은 연산이 키 규약(`:v`, `:bold`)에 의존한다. 이 규약은 store 안에만 있고 밖으로는 타입 있는 API(`getCellValue` 등)로만 노출된다.

### 셀 서식 (S4): boolean 값, 꺼짐 = 키 삭제

서식 4종(굵게·기울임·밑줄·취소선, D3)은 평탄 키(`"r:c:bold"`)에 `true`로 저장하고, 끄면 키를 지웁니다.

- **선택**: boolean + 키 삭제. 값 키의 "빈 값 = 키 삭제" 규약과 대칭이고 `false` 잔여 키가 남지 않는다. 대안(문자열 `"1"`)은 맵 타입은 좁게 유지하지만 파싱 규약이 하나 더 생긴다.
- **범위 토글**: "하나라도 꺼져 있으면 모두 켜기"(S4) 판정 후, 이미 맞는 상태의 셀은 건드리지 않는다 — undo 1회가 토글 전의 섞인 상태를 정확히 복원한다.
- **알려진 경계 사례**: 두 탭이 같은 꺼진 셀을 거의 동시에 켜면 LWW로 한쪽 항목만 남는데, 그 승자가 undo하면 패자의 "켜기" 의도까지 함께 사라진다. Yjs UndoManager의 표준 동작이고 D7("Yjs 기본 동작")이 수용하는 범위이며 수렴은 유지된다 — 회피하려면 undo 시 동시 편집 겹침 감지가 필요해 비용 대비 이득이 없다.

### 툴바와 선택 상태: 커서 미러

툴바(서식 버튼 눌린 상태, 적용 대상 범위)는 Grid 내부의 선택 상태가 필요하지만 Grid의 형제 컴포넌트입니다.

- **선택**: Grid가 이미 awareness 복사용으로 노출하는 `onPresenceChange(cursor)` 콜백을 재사용해 SheetScreen이 커서를 React state로 미러링, Toolbar에 내린다. 원본은 여전히 Grid의 `useSelection` 한 곳(Q2)이고 미러는 단방향 사본이다.
- **검토한 대안**: `useSelection`을 SheetScreen으로 리프트 — 선택 로직(키보드·드래그)이 Grid에 묶여 있어 feature 내부 훅을 공개해야 하고 API 표면이 커진다. Grid에 툴바 슬롯 — 툴바 레이아웃(참여자 목록과 나란히)이 SheetScreen 소유라 어긋난다.

### 단축키 매칭은 e.code (물리 키)

한글 자판이 활성이면 `e.key`가 `'b'` 대신 `'ㅠ'`로 보고되어 ⌘B·⌘Z가 동작하지 않습니다. 한국어 입력이 핵심 시나리오(S2)인 앱이라 레이아웃 독립적인 `e.code`(`KeyB`, `KeyZ` 등)로 매칭합니다. 서식 단축키는 IME 조합 가드보다 앞에 두어 조합 중에도 동작합니다 — ⌘/Ctrl 조합은 조합 입력이 아니고 셀 텍스트를 건드리지 않기 때문입니다.

### AI 편집 (3단계): 하위 묶음 분할과 제안 상태 위치

AI 편집은 A1~A7·X1~X3으로 커서 3개 하위 묶음으로 나눠 진행합니다: ①제안 생성·검토·적용(단일 탭, 현재 구현) → ②스트리밍·취소·실패(OpenRouter Route Handler) → ③멀티탭 충돌·표시(X1~X3). 가장 큰 위험(제안 상태 모델·배치 적용·undo·스키마)을 LLM 없이 먼저 고정하기 위한 순서입니다.

- **제안 소스를 함수로 주입** (`ProposalSource`): 묶음 1은 mock, 묶음 2에서 실제 스트리밍 클라이언트로 교체한다. store·UI 시그니처를 바꾸지 않고 LLM 없이 검토·적용 경로를 완결 검증할 수 있다(provider 경계 예외).
- **제안·base 스냅샷은 AI feature 로컬 상태**(Y.Doc에 넣지 않음): 적용 전 제안은 확정되지 않은 개인 초안이라 동기화 대상이 아니다. `doc.transact`를 타지 않으므로 다른 탭에 새지 않는다(X2 근거). 요청 시점의 base를 고정해 두면 묶음 3의 충돌 비교(base≠현재, X1) 재료가 확보된다.
- **적용은 배치 op `applyCellValues`로 한 transact**(A5): UndoManager가 undo 1단계로 캡처한다. 적용 앞뒤로 `stopCapturing()`을 호출해 직전·직후 입력과 합쳐지지 않게 한다. `stopCapturing`은 store가 아니라 proposal-store가 호출한다 — "store는 전송·저장(undo 포함)을 모른다"는 경계를 유지하기 위해 store는 순수 transact만 노출한다.
- AI는 **값만 제안**한다(서식은 컨텍스트로 읽어 보내되 제안 대상 아님). 컨텍스트(D9)는 값 있는 셀의 sparse 목록 + 선택 범위 + 활성 셀이다.

### 시트 목록 (S8): 별도 feature·별도 Y.Doc, 루트에서 공유

여러 시트를 만들고 오갈 수 있어야 합니다(`/`=목록, `/sheet/[id]`=편집).

- **별도 feature `sheet-list`**: 시트 목록은 셀 도메인이 아니라 `features/sheet`에 넣지 않고, `collab`은 시트 개념을 금지하며, `session`은 조립 전용이다. 목록 데이터·ops는 새 feature가 소유한다.
- **별도 Y.Doc(`sheet-registry`)**: 시트 목록은 셀과 독립적으로 동기화·영속되어야 하므로 전용 문서를 둔다. 셀과 같은 평탄 키(`"{id}:name"`, `"{id}:createdAt"`)로 저장해 동시 생성 시 컨테이너 LWW 소실을 막는다. 참여자 개념이 없어 provider의 `awareness`를 optional로 두고 목록 doc에는 넘기지 않는다.
- **목록 세션을 루트 레이아웃에서 공유**: `/`와 `/sheet/[id]`가 같은 registry doc 인스턴스를 쓴다. 각 화면이 별도 세션을 만들면, 생성 직후 이동한 편집 화면이 아직 IndexedDB에 flush되지 않은 시트를 못 찾고(재브로드캐스트할 이전 provider도 이미 해제됨) "찾을 수 없음"에 갇힐 수 있다. 공유하면 방금 만든 시트를 게이트가 즉시 본다.
- **존재 확인 후에만 시트 세션 마운트**: 없는 id 접속이 빈 `sheet-{id}` IndexedDB를 만들지 않게 한다. 목록 로드 전에는 판정할 수 없어 로딩을 표시하고, 다른 탭이 방금 만든 시트라면 동기화가 도착하는 대로 자동으로 편집 화면으로 전환된다.
- **시트 삭제(P2)와 목록 doc의 UndoManager는 제외** — 삭제는 위 "구현 범위" 참고, undo는 셀 편집 스코프라 시트 생성이 ⌘Z로 사라지지 않는다.

### 셀 데이터는 1단계(단독 편집)부터 Y.Doc에

공동 편집(2단계) 전에는 React 상태로도 충분하지만, 그렇게 시작하면 2단계에서 저장 구조·편집 연산·구독을 전부 다시 쓰고 그 사이 "상태는 한 곳에만" 규칙을 위반한 상태를 거칩니다.

- **선택**: 처음부터 `cells: Y.Map`에 저장하고, UI는 store의 `subscribe`/`getCellValue`(`useSyncExternalStore`)로만 읽는다. 로컬 편집은 전부 `LOCAL_ORIGIN` transact로 실행한다.
- **검토한 대안**: React `Map` 상태로 시작 — 1단계 코드는 약간 단순하지만 2단계에서 전면 재작성.
- **트레이드오프**: provider 없는 Y.Doc은 관찰 가능한 Map일 뿐이라 1단계 비용은 거의 없다. 2단계에서는 session에 persistence·provider·UndoManager만 추가하면 되고 store·UI는 바뀌지 않는다.

### 셀 편집기: 항상 포커스를 유지하는 단일 input

한글(IME)로 "바로 입력"을 시작할 때 첫 글자가 유실되지 않아야 합니다(S2 P0). 편집 진입 시 input을 마운트하고 포커스를 옮기는 방식은 `compositionstart`가 포커스 이동 전에 발생해 첫 글자가 빠지거나 분리됩니다.

- **선택**: input 하나를 항상 포커스해 활성 셀 위에 투명하게 두고, 편집 모드에서만 보이게 전환한다. 조합이 시작된 요소가 그대로 편집기가 되므로 IME가 끊기지 않는다. 조합 중 특수 키는 `isComposing`으로 한 곳(`useGridKeyboard`)에서 무시한다.
- **검토한 대안**: 편집 진입 시 input 마운트 — 코드가 직관적이지만 IME 첫 글자 유실(S2 P0 결함).
- **트레이드오프**: 포커스를 이 input에 유지·복구하는 관리 코드가 필요하다(셀 pointerdown에서 재포커스).

### 명세 해석: 비편집 상태의 Enter는 편집 모드 진입 (D12)

S2(Enter=이어서 편집)와 S3 표(Enter=아래로 이동)가 충돌해 하나를 골라야 했습니다.

- **선택**: Google Sheets와 같은 "편집 모드 진입". Enter로 편집 시작 → 다시 Enter로 확정 후 아래 이동. `docs/spec.md` S3 표를 함께 수정했다.
- **검토한 대안**: Excel식 "아래로 이동" — 편집 진입 수단이 F2·더블클릭만 남아 키보드 위주 사용이 불편.

### 폴더 구조와 의존 방향

같이 바뀌는 코드끼리 모으기 위해 기술 종류(components, hooks 등)가 아니라 **기능 단위**로 나눴습니다.

```
src/
  app/                 # 라우트만
  features/
    sheet/             # 셀 주소·범위(model), Y.Doc 구조·편집 연산·undo(store), 그리드 UI(ui)
    collab/            # IndexedDB 영속화, BroadcastChannel 동기화, presence
    ai/                # (3단계) AI 편집
  session/             # 기능 조립: Y.Doc·저장·동기화·undo 생성과 해제
  shared/              # 기능과 무관한 공통 UI·유틸
```

```
ai ──→ sheet ←── collab/ui
         ↑
      session (조립)
```

- **`sheet`는 `collab`·`ai`를 모릅니다.** 탭이 하나든 여러 개든 똑같이 동작하는 편집 로직만 담습니다.
- **`collab` 코어는 Y.Doc만 다룹니다.** 셀이라는 개념을 몰라서, 네트워크 동기화로 확장할 때 이 폴더의 provider만 교체하면 됩니다. 그리드 위에 다른 참여자의 선택 범위를 그리는 `collab/ui`만 `sheet`의 공개 API를 사용합니다.
- **기능 사이의 연결은 `session`에서만** 합니다.
- **각 feature는 `index.ts`로만 공개**합니다. 내부 파일 직접 import와 위 의존 방향 위반은 ESLint `no-restricted-imports`로 막습니다.
- **그리드 위 표시는 레이어로 끼워 넣습니다.** `Grid`는 좌표 계산과 오버레이 자리만 제공하고, 다른 참여자의 선택 표시나 AI 제안 하이라이트는 각 feature가 자기 레이어로 전달합니다. `Grid`가 이들을 직접 import하면 `sheet`가 `collab`·`ai`에 의존하게 되기 때문입니다.
- 각 feature 안에서는 순수 로직(`model/`)과 외부에 닿는 코드(Yjs, IndexedDB, React)를 나눠 순수 로직을 단위 테스트합니다.
